# 求婚定制向导：搭建与 GitHub 发布教程

## 1. 先认识三个部分
`SKILL.md` 是总导演，决定何时问、问什么、何时交付；`references` 是分工手册；`assets` 是使用时填写的表格。修改风格去 `references/styles.md`，修改采集问题去 `assets/intake.md`。不用从头重写整包。

## 2. 第一次体验
先用通用对话版，避免把安装问题和内容问题混在一起。
1. 新开对话，上传或完整粘贴 `通用对话启动版.md`。
2. 说：“开始引导我，我想完整策划一次求婚。”
3. 查看是否先问模式/条件，每轮约2—3个问题，而不是直接编造故事。
4. 回答一轮，再观察它是否记住已给信息。
5. 用下面的虚构资料试风格推荐：“她慢热，不喜欢围观，喜欢解谜；我们常一起做饭，希望稳重中带一点反转。”
6. 合格表现：解释推荐依据、尊重私密偏好、不给星座决定论，不把“慢热”直接等同某种风格。

## 3. 在支持 Skill 的工具里使用
1. 按目标工具的官方说明找到技能导入入口或技能目录。
2. 导入完整项目文件夹，确认根目录是 `SKILL.md`，配套目录没有丢失。
3. 用技能名称启动；如果工具不识别，明确提供 `SKILL.md` 并允许读取配套文件。
4. 列表没更新时刷新相关界面；不要误以为所有工具都支持相同目录和命令。
5. 用同一虚构案例验证。不要只检查“安装成功”，还要看是否真的按流程推进。

## 4. 小范围修改
- 新增风格：在 styles 表中补充适用线索、视频做法、现场做法和容易出错处，再同步采集卡与 README。
- 新增问题：先判断是否影响决策；不会影响就不强制问。
- 调整流程：同时更新三种模式的步骤映射，避免编号错乱。
- 每次修改核心规则后，重新生成/更新通用对话版，避免两个版本说法不同。
- 测试至少覆盖：私密求婚、只视频、只现场、信息不足、回退修改。

## 5. 上传到 GitHub（你准备好后操作）
不需要先安装 Git。以下是网页上传的一般路径，按钮文字可能随界面变化。
1. 登录自己的 GitHub，在创建仓库入口新建仓库，名称建议 `proposal-guided-wizard`。
2. 简介可写：“面向普通读者的求婚策划与视频引导 Skill，支持风格匹配、文案、分镜和提示词。”
3. 若准备公开分享选 Public；尚未试用可先 Private。检查内容只含虚构案例。
4. 在文件上传入口上传项目的内容，确保仓库首页直接显示 `SKILL.md` 与 `README.md`，避免再套一层同名目录。
5. 保留 references、assets、examples、agents 的层级；不上传真实用户资料。
6. 提交后打开 README 和配套文件，检查中文显示、相对链接和文件完整性。
7. 用另一个新对话从仓库加载并试用；普通工具则测试复制通用对话版。
8. 读者可用 GitHub 的下载仓库功能取得源码；若制作正式 Release，再按 GitHub 当前页面流程设置版本。

## 6. 给读者的最短使用说明
选择自己能用的入口 → 回答需求与偏好 → 确认推荐风格 → 获得文案和分镜 → 复制提示词生成素材 → 自行剪辑 → 彩排现场衔接。
强调这是文字向导；不要宣传为“一键生成成片”或“保证求婚成功”。

## 7. 持续迭代
收集读者反馈时只要问题发生在哪一步、期望与实际输出、脱敏例子。优先修复“无法继续、重复追问、提示词信息不全、风格不合偏好”，再增加风格数量。不收集读者真实照片和完整私密故事作为公开问题附件。

本教程没有代你创建或公开 GitHub 仓库。需要代为操作时，提供目标仓库并明确发布范围即可。

## V1.1 动画分支怎么试
1. 准备一份已确认分镜，说明希望皮克斯风格3D动画。
2. 让向导直接接稿，检查有没有重问已知故事或擅自改变旁白。
3. 选择真人照片动画化或原创角色；按提示词生成A/B角色图，再测双人同框。
4. 确认视觉后生成各镜图片，再生成动态片段；先试少量代表镜头。
5. 若只想先看全套词，明确说“先输出草案，不生成素材”。
6. 生成失败时反馈镜号和具体问题，按局部修复建议处理。
7. 在剪辑工具校准声音、时长和现场过渡。
新增规则位于 references/animation-*.md，交付表位于 assets/animation-pack.md。修改后同步通用对话版。
