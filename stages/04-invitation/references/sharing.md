# 微信分享与海报交付

## 完整顺序

采集照片和资料 → 保存项目 → 三款预览与 BGM → 选定风格 → 补齐资料或明确演示 → 生成最终页 → 发布整个目录 → 确认宾客访问范围 → 回填实际 public_url 并更新原站 → 验证入口与媒体 → 判断分享方式 → 制作海报或配置微信分享 → 检查并交付 → 修改后更新同一项目。

沿用用户已选择的风格、封面、资料、链接和公开范围。缺少能力时推进独立步骤，准确报告待完成项。单次请柬制作不要求用户先注册公众号或买域名。

## 先分清分享效果

| 用户要的效果 | 操作 | 交付边界 |
| --- | --- | --- |
| 亲友打开网页 | 发布无需宾客登录的访问链接 | 本地附件、私人预览地址和有标题的 Markdown 链接都不能充当微信卡片 |
| 有标题及照片的分享图片 | 生成同风格海报，绑定实际请柬 URL 的二维码 | 好友保存或接收图片后，在微信长按识别；图片本身没有点击跳转能力 |
| 点击微信标题卡片进入 | 评估实际托管域名、账号分享接口权限及服务端签名能力 | title、Open Graph 和 navigator.share 的标题字段均不构成微信显示保证，必须真机测试 |

用户反馈微信只显示网址时，先核对截图或实际分享入口，再检查网页标题、分享元数据和当前平台的微信分享能力。不要承诺改一行标题就解决，也不要把对话中的命名链接冒充微信可点击文字。

未提供公众号和自有域名时，说明现有网页仍可访问，推荐海报路径。用户选择海报后直接制作，不再询问这些条件。坚持标题卡片时再评估有权限的微信账号、可配置的实际域名和服务端环境；确认当前官方文档及账号权限后再接入 JS-SDK。密钥与签名服务只留在服务端，不放入 Skill 或公开静态文件。第三方平台可能要求重做请柬，未核实导入能力前不要承诺原网页可直接迁移；不替用户购买服务或上传照片到未选择的服务。

## 海报生成

使用 scripts/share_poster.py。读取当前配置或 project.json，沿用 style、cover_index、新人称呼、event_type、date、venue、三项时间和 public_url。海报优先使用自定义 share_title，否则使用宴会类型加“请柬”。与网页不同，海报文字会成为图片的一部分，继续修改必须重建。share_description 用于网页分享元数据。

海报为1080×1920 PNG，三款配色分别对应红白双喜、花影与酒红金色。完整放入封面照片，矫正方向并省略源图片元数据；即便网页设为 cover，海报仍采用 contain，以便完整展示人物。横图保留比例和留白。长姓名、场地、文案自动缩字号，无法在最低字号完整排下时明确失败，旧版保留；不要截断地址或重要时间。海报省略详细地址，宾客通过请柬查看。

依赖为 Pillow、qrcode、fonttools。本机可选 zxing-cpp 用于程序解码。先用 doctor.py 检查能力，再按宿主权限准备环境；不擅自安装全局软件。中文字体通过 --font 和可选 --bold-font 指定本地有权使用的 TTF/OTF/TTC，默认查找常见系统中文字体；不内置用户机器路径或自动下载字体。缺字直接报错，不能交付方框乱码。

正式海报：
```bash
python3 scripts/share_poster.py --config <project.json> --out <sharing/poster.png> --font <中文字体.ttf> --online-report <checks/online.json> --report <sharing/sharing.json>
```

online.json 必须对应当前配置、当前 style 和准确的 public_url，并同时通过 static 与 online 检查。没有自动检查能力但用户已经实测该地址可打开时，可改用 --url-evidence "用户于 YYYY-MM-DD 确认该链接在微信可打开"；报告区分 user_confirmed 与自动 passed。只把用户报告过的项目写为已测，不推断分享卡片、音乐或双端手机也通过。

演示海报额外添加 --allow-demo；已知使用 AI 演示照片时添加 --demo-note "AI 照片、姓名、婚期及场地均为示例"，保留页脚标记。信息不全时显示待确认，不虚构婚期和场地。尚未确认链接时，仅显式 --allow-unverified-url 制作带“链接待验证”的候选海报；不作为可用分享成品交付。public_url 为空时停止二维码制作，先完成发布。

海报、项目资料和 sharing.json 均放在网页发布目录外。脚本拒绝覆盖配置、原图、字体及线上报告，出错时保留旧海报。二维码在本机编码，保留白色四模块静区、深色图案和整数模块，不叠加头像、不依赖第三方二维码服务、不交给生成式图片工具绘制。

## 验证、交付与续做

1. 对照当前选定模板核对标题、人物、封面、新人称呼、日期、场地和时间；查看海报原图及手机缩略图，检查字号、裁切、二维码和演示标记。
2. 有 zxing-cpp 时脚本解码1080、540、360px宽度的整张海报，并逐字比较当前 URL。失败不覆盖旧海报；没有解码器时明确二维码程序验证待完成。
3. 在微信发送图片后长按识别，核对落地页及访问权限。程序解码仅证明编码可读，不能代替微信实测、无登录访问或页面内容检查。
4. 保存 sharing.json：包含配置、封面照片、海报摘要和 URL，以及访问、解码、视觉、微信各项状态。脚本默认视觉与微信为 pending；Agent 实际检查后记录方法、结果和日期。
5. 交付可下载的海报原图及请柬链接，说明“保存图片发给好友，好友长按识别进入”。附实际资料状态与未测项；用户允许公开链接也不等于授权向联系人发送消息。
6. 修改称呼、日期、时间、场地、模板、封面、短句或链接后，重新生成网页及海报，刷新分享记录。仅改变 BGM 或粒子时可沿用相同海报图片，但核对落地页已更新，重新关联当前配置摘要；旧地址二维码不得继续冒充最新链接。
7. 宿主有文件保存能力时持久保存海报、私有项目及分享记录，保持已有文件身份；代码项目若已有外部 Git 托管则沿用其保存流程。不可把临时目录存在视为已持久保存。无保存能力时如实交付下载文件和需保存项目，不承诺以后自动续做。

交付示例：“红白双喜海报已生成，二维码程序解码通过，指向当前请柬。保存后作为图片发给好友，长按识别即可进入。当前为演示资料，微信长按识别仍需实机确认。” 仅按真实状态替换这段措辞。
